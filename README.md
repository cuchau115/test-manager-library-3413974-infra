# test-manager-library-3413974-infra

> **Prueba técnica · Ficha ADSO 3413974**
> Horario: de **9:15 a. m. a 3:00 p. m.** (15:00). Después, **feria de presentación** de cada proyecto.

Este repositorio es la **infraestructura** de *Manager Library*: contenedores, red, volúmenes y el motor de base de datos vacío. **Empieza vacío a propósito**: se construye en el fork de cada aprendiz.

## Instrucciones

Cada aprendiz debe **crear el fork** de los seis repositorios del proyecto y **resolver el proyecto
con el spec planteado**.

1. Hacer fork, a su cuenta de GitHub, de cada repositorio de la tabla del final.
2. Leer el spec en [`test-manager-library-3413974-docs`](https://github.com/code-sena/test-manager-library-3413974-docs).
   Se entrega en dos versiones: `spec-python/` y `spec-.net/`.
3. Desarrollar en los forks.

## El reto se desarrolla con React y PHP (Laravel)

El spec está escrito para Python y para .NET, pero el reto **no** se hace en esos lenguajes:

| Capa | Tecnología del reto |
|---|---|
| Frontend | React |
| Backend | PHP con Laravel |

Lo que el spec define sobre el negocio —historias, criterios de aceptación, reglas, contrato de la
API, modelo de datos— se respeta. Lo que define sobre la tecnología se traduce a React y Laravel.

## La prueba no consiste en escribir el código

El propósito principal es ver la **capacidad de desempeño con SDD** (*Spec-Driven Development*,
desarrollo guiado por especificación): cómo se lee, se interpreta y se aplica una especificación
para llevarla a un stack distinto. El código es el medio, no el fin.

## Feria de presentación

Al cerrar la prueba (3:00 p. m.) cada aprendiz **presenta su proyecto** al grupo: qué construyó del spec, qué dejó fuera y por qué,
y una demostración corta de lo que funciona (la aplicación y el sitio público). Lo que se presenta es lo que quedó **subido a los forks
antes de las 3:00 p. m.**: no se presenta nada que no esté en GitHub.

## Arranque local

Desde este repositorio, copia `.env.example` a `.env` y configura `APP_KEY`, `JWT_SECRET` y las
credenciales iniciales del administrador. Luego levanta todo el sistema con un solo comando:

```sh
docker compose up --build -d
```

Compose espera a que PostgreSQL esté saludable; la API ejecuta sus migraciones y crea el administrador
de forma idempotente al iniciar. Comprueba el estado y la salud de los servicios con:

```sh
docker compose ps
curl -fsS http://localhost:8000/health
```

La API queda en `http://localhost:8000`, React en `http://localhost:5173` y el sitio público en
`http://localhost:8080`.

Para generar los datos de demostración (40 libros, 10 socios, 15 préstamos y 3 líneas vencidas),
ejecuta el perfil opcional del sembrador:

```sh
docker compose --profile tool run --rm tool
```

El servicio `tool` llama solo a la API; no conecta directamente a PostgreSQL. El parámetro de fecha
retroactiva para las tres líneas vencidas está limitado al entorno local, según ADR-RL-006.
